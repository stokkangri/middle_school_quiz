The big idea

Pick any start and destination — not only “straight up the field.” An IMU tells you heading error (how many degrees you face the wrong way). Controllers turn that error into steering. A constant “push” (carpet, weak motor) makes the differences easy to see.

error = desiredHeading − measuredYaw → steer = Kp·e + Kd·ė (+ Ki·∫e for PID)

The control ladder

Simple ranking for first-year FTC drive / heading hold:

  1. None Open-loop: motors get a fixed command. Drift and side-push send you past the goal.
  2. P Steers harder when more off-heading. Reaches the corridor but often wiggles (overshoot).
  3. PD Adds damping from how fast error is changing. Same push, smoother path, smaller error spikes.
  4. PID Can cancel a stubborn leftover bias — but on short FTC autos it often winds up and overshoots. Optional later.

Remember: no control < P < PD for most teleop/auto line drives. PID is not automatically “best” — it has tradeoffs (see below).

Proportional only

P means: “the farther off I am, the harder I steer back.”

  • Beats none — you actually aim at the goal
  • Still misses how fast error is changing
  • Often overshoots → snake / wiggle on the path graph

On the heading-error graph, P usually swings past zero and back. That oscillation is what D is for. 

# Python-style (P only) — any direction to goal
desired = angle_to(goal)      # not always 0°!
error = wrap(desired - yaw)
steer = Kp * error
drive(speed - steer, speed + steer)  # each arg is one side: both motors on that side

Add differential (D)

D watches change in error: “If I’m slamming toward the line, ease off.”

  • Same side push as P — smaller wiggles
  • Error graph hugs zero sooner
  • Usually best simple choice for FTC line drives

Ladder check: PD’s path stays nearer the dashed S→G line than P or none. 

# Python-style PD
error = wrap(desired - yaw)
d_error = error - prev_error
steer = Kp * error + Kd * d_error
prev_error = error
drive(speed - steer, speed + steer)  # both motors on each side
# sleep(0.02)  # steady loop time matters for D

How it looks in FTC

Blocks sketch · OnBot Java · Python-style text — same math.

when opMode is active ▾
set desired to angle toward goal
set error to desired − yaw
set dError to error − prevError
set steer to Kp × error + Kd × dError

Teaching sketch — real FTC Blocks use REV IMU / motor block names. “Left” and “right” are side powers: copy each one to both motors on that side.

// OnBot Java — PD toward a field point (any heading)
double Kp = 1.6, Kd = 0.85;
double prevError = 0;

while (opModeIsActive() && !atGoal()) {
    double desired = angleToGoal(pose, goal); // degrees
    double yaw = imu.getRobotYawPitchRollAngles().getYaw(AngleUnit.DEGREES);
    double error = AngleUnit.normalizeDegrees(desired - yaw);
    double dError = error - prevError;
    double steer = Kp * error + Kd * dError;
    prevError = error;
    // One power per side. Both wheels on that side share it.
    double leftPower = Range.clip(speed - steer / 100.0, -1, 1);
    double rightPower = Range.clip(speed + steer / 100.0, -1, 1);
    frontLeft.setPower(leftPower);
    backLeft.setPower(leftPower);
    frontRight.setPower(rightPower);
    backRight.setPower(rightPower);
    sleep(20);
}
desired = angle_to(goal)   # works on diagonals too
error = wrap(desired - get_yaw())
d_error = error - prev_error
steer = Kp * error + Kd * d_error
prev_error = error
# left side → both left motors; right side → both right motors
drive(speed - steer, speed + steer)

PID on the ladder — why “more letters” ≠ always better

In the lab, turn on PD vs PID. With a big constant push, PID may finally cancel bias — but watch the error graph for a late swing: that is integral windup.

Disadvantages of I for many FTC autos
  • Windup — error piles up while you cannot yet correct; then the robot overshoots hard.
  • Short moves — I needs time; a 2-second segment may end before I helps.
  • Extra tuning — Ki fights Kp/Kd; first-year teams get lost.
  • Reset rules — must clear the integral when the target changes or you stop.
When I can still be useful

Long hold against a steady bias (teleop heading lock on a tilted field, weak motor). Even then: clamp the integral and reset often. 

integral += error * dt
integral = clamp(integral, -maxI, maxI)   # required!
steer = Kp*error + Ki*integral + Kd*d_error

PIDF — F is feedforward

FTC motor controllers add one more letter. P, I, and D all react to error (target minus what you measured). F uses the target itself and adds the power that target usually needs, including when the error is already zero.

power = Kp·e + Ki·∫e + Kd·ė + Kf·target

What F is doing

F is a guess of motor power for the speed you asked for, as if nothing were fighting the motor. At 800 ticks/sec the speed error is about 0, so P adds almost nothing — F still applies Kf × 800, which is what keeps the motor at that speed. P cleans up the miss. REV’s starter sets D to 0 and a small I (about a tenth of P). F is why I does not have to hold the speed by itself.

Where it lives in FTC

It runs on the hub, in velocity mode. RUN_USING_ENCODER plus setVelocity(ticksPerSec) uses the formula above. The heading PD on this page is code you write. The hub’s full-power number is 32767, so Kf = 32767 / maxTicksPerSec. REV’s starter then sets Kp = 0.1×Kf, Ki = 0.1×Kp, and Kd = 0. Measure max ticks/sec at full power with a full battery, in RUN_WITHOUT_ENCODER. 

// OnBot Java — each wheel motor is its own DcMotorEx. Same coefficients on all four.
double maxTicksPerSec = 2800;                  // full power, RUN_WITHOUT_ENCODER
double kF = 32767.0 / maxTicksPerSec;          // power guess for that speed
double kP = 0.1 * kF;                          // REV starter
double kI = 0.1 * kP;
DcMotorEx[] drive = { frontLeft, backLeft, frontRight, backRight };
for (DcMotorEx m : drive) {
    m.setVelocityPIDFCoefficients(kP, kI, 0, kF);
    m.setMode(DcMotor.RunMode.RUN_USING_ENCODER);
    m.setVelocity(800);   // ticks/sec — hub adds Kf*800, then P/I/D fix the miss
}

If the motor type is set in the robot configuration, the hub already has a PIDF. setVelocityPIDFCoefficients replaces those numbers for this OpMode after you measure the motor. Apply them again at the start of every OpMode — the hub forgets them when the OpMode ends.

Distance is a second job

The heading examples above only answer “which way am I facing?” They never read how far the wheels have turned. Going 24 inches is a separate encoder check: calibrate ticks per inch once, then keep driving until the count reaches the target. That stop condition is ordinary comparison, not part of the heading PID.

Distance — usually just matching

  • Calibrate once: ticksPerInch from gear ratio and wheel size, or from a measured test drive.
  • targetTicks = inches × ticksPerInch
  • Each loop: average all four encoders, stop when that average reaches targetTicks.

You can turn leftover ticks into forward speed yourself (forward = KpDist × ticksLeft). RUN_TO_POSITION does that on the hub: position P picks a target speed, then the velocity PIDF — including F — holds it. Still a second controller beside heading: one number is forward, the other is steer.

Heading — the PD (or PID) you write

  • Read the IMU yaw.
  • steer = Kp·headingError + Kd·Δerror
  • Both motors on the left get forward − steer. Both on the right get forward + steer.

Same 20 ms loop. Distance picks forward and when to quit. Heading picks steer. Four motors still means two numbers — one per side. F, when you use setVelocity, runs on each motor and holds the speed you gave that wheel.

Set each motor’s direction so positive power drives the robot forward. Then every encoder counts up while you drive ahead, and the average of the four readings is how far the center of the robot has gone. One wheel alone is a bad ruler: steering slows that side, and a single wheel can slip. 

// Four motors, two side powers. Distance = average of all four encoders.
// Optional: RUN_USING_ENCODER so each hub PIDF (with F) holds that wheel's speed.

double ticksPerInch = 45;                 // calibrate on your robot
int targetTicks = (int) (24 * ticksPerInch);
double desiredHeading = 0;                // degrees
double kP = 0.02, kD = 0.001;             // heading → power
double prevError = 0;

DcMotor[] wheels = { frontLeft, backLeft, frontRight, backRight };
for (DcMotor m : wheels) {
    m.setMode(DcMotor.RunMode.STOP_AND_RESET_ENCODER);
    m.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);   // ticks still count
}

while (opModeIsActive()) {
    int traveled = (frontLeft.getCurrentPosition() + backLeft.getCurrentPosition()
                  + frontRight.getCurrentPosition() + backRight.getCurrentPosition()) / 4;
    if (traveled >= targetTicks) break;    // distance match — not the heading PID

    double yaw = imu.getRobotYawPitchRollAngles().getYaw(AngleUnit.DEGREES);
    double error = AngleUnit.normalizeDegrees(desiredHeading - yaw);
    double steer = kP * error + kD * (error - prevError);
    prevError = error;

    double forward = 0.45;                 // constant until the average says stop
    double leftPower = Range.clip(forward - steer, -1, 1);
    double rightPower = Range.clip(forward + steer, -1, 1);
    frontLeft.setPower(leftPower);
    backLeft.setPower(leftPower);
    frontRight.setPower(rightPower);
    backRight.setPower(rightPower);
}
for (DcMotor m : wheels) m.setPower(0);

// Velocity PIDF version — F runs separately inside each motor:
//   double base = 900;                 // ticks/sec
//   double steer = 12 * error;         // ticks/sec per degree
//   frontLeft.setVelocity(base - steer);
//   backLeft.setVelocity(base - steer);
//   frontRight.setVelocity(base + steer);
//   backRight.setVelocity(base + steer);

Four motors, two numbers. Both left wheels get forward − steer. Both right wheels get forward + steer. Distance is the average of the four encoders. Feedforward is the hub’s extra term on each motor when those commands are target speeds. Strafe is a third request — the next section adds it on top of these two.

Move + strafe + turn

Setting one power on each wheel showed what the robot does. Those demos are the recipe: each maneuver is a pattern of signs. Driving with all three at once adds the three patterns on every wheel. A “+” below means that wheel’s positive power — the direction you already set so the robot drives forward.

Sign of each wheel for one positive request
Wheel Move forward Strafe right Turn clockwise
Front left + + +
Back left + − +
Front right + − −
Back right + + −
frontLeft = move + strafe + turn backLeft = move − strafe + turn frontRight = move − strafe − turn backRight = move + strafe − turn

Why the strafe column looks like that

Mecanum rollers sit at 45°. A spinning wheel pushes the robot both forward and sideways. All four wheels forward: the sideways pushes cancel and the robot drives straight. Strafe right spins one diagonal forward (front left and back right) and the other diagonal backward: the forward pushes cancel and the sideways pushes add.

One set of numbers

Move 0.50, strafe 0.20, turn 0.10 (clockwise):

  • Front left: 0.50 + 0.20 + 0.10 = 0.80
  • Back left: 0.50 − 0.20 + 0.10 = 0.40
  • Front right: 0.50 − 0.20 − 0.10 = 0.20
  • Back right: 0.50 + 0.20 − 0.10 = 0.60

Sign is direction. Size is speed.

A motor only accepts power from −1 to 1. If the three requests add past that, divide every wheel by max(|move| + |strafe| + |turn|, 1). The mix stays the same; the robot shares the speed it has. Requests of 0.8, 0.8, and 0.8 use a scale of 2.4. 

// Three requests → four wheel powers. +turn is clockwise.
double move = 0.50;
double strafe = 0.20;
double turn = 0.10;

double frontLeftPower  = move + strafe + turn;
double backLeftPower   = move - strafe + turn;
double frontRightPower = move - strafe - turn;
double backRightPower  = move + strafe - turn;

double scale = Math.max(Math.abs(move) + Math.abs(strafe) + Math.abs(turn), 1.0);
frontLeft.setPower(frontLeftPower / scale);
backLeft.setPower(backLeftPower / scale);
frontRight.setPower(frontRightPower / scale);
backRight.setPower(backRightPower / scale);

The heading loop already produces steer: positive steer speeds the right side and slows the left. Clockwise turn is the opposite sign, so turn = -steer. With strafe at 0, both left wheels get move − steer and both right wheels get move + steer — the same side powers as the loop above. Strafe is the extra request (the sideways stick, or 0 when an auto should drive straight). Move still comes from the encoder distance. Turn still comes from the heading PD. 

// Same distance + heading loop, now with a strafe term.
double move = 0.45;                         // encoder distance, or the forward stick
double strafe = gamepad1.left_stick_x;      // 0 in an auto that should not slide
double steer = kP * error + kD * (error - prevError);
double turn = -steer;                       // page steer speeds the right side

double fl = move + strafe + turn;
double bl = move - strafe + turn;
double fr = move - strafe - turn;
double br = move + strafe - turn;
double scale = Math.max(Math.abs(move) + Math.abs(strafe) + Math.abs(turn), 1.0);
frontLeft.setPower(fl / scale);
backLeft.setPower(bl / scale);
frontRight.setPower(fr / scale);
backRight.setPower(br / scale);

Class checklist

  1. Set path angle ≠ 0 so S→G is diagonal. Restart race.
  2. Mode None + P + PD, side push ~40. Compare who hits G.
  3. Read heading error graph: none stays wrong; P oscillates; PD settles.
  4. Mode PD vs PID, raise Ki — look for late overshoot (windup).
  5. Say the ladder out loud: none < P < PD; PID is optional with risks.
  6. Read PIDF: F holds target speed; encoder distance is a separate stop check in the same loop as heading steer.
  7. Read Strafe: move, strafe, and turn are three sign patterns. Add them on each wheel. turn = -steer.
